# 测量设计:在线求解开销的记账口径(dispatch-latency accounting)

- **背景**(顾问要求):"1ms CPU = 1ms 完成时间"不总成立——GPU 忙时求解耗时被掩盖,GPU 空闲等待决策时才会直接造成派发延迟。必须分开统计,不能用简单相加。
- **实现**(`scripts/milp_v0_performance.py` + 策略内计数):

## 1. 每次决策记录

MILP 在线策略(`milp_v0a`)在每个决策点记录:

| 计数 | 含义 |
|---|---|
| `milp_decisions` | 决策次数 |
| `milp_executed` | 首动作在候选池内、实际执行的次数 |
| `milp_fallback` | 求解失败/不可行/无立即动作 → 回退 PDRS 的次数 |
| `milp_gap_fallback` | 首动作不在 DES 候选池(预测差距)→ 回退的次数 |
| `milp_solve_ms` | 求解 CPU 总耗时(含观测构建) |
| **`milp_exposed_ms`** | **暴露延迟**:当被选设备在决策时刻**空闲**(`busy_until ≤ now`)时,求解耗时**直接推迟派发**,计入暴露;设备忙时求解与执行重叠,记为隐藏 |

## 2. 净收益的三种读法(分别报告,不混合)

1. **纯调度效果**(不计开销):mean/p95 的配对差(当前主口径);
2. **暴露延迟修正**:`净收益 = 调度收益 − 暴露延迟`(暴露延迟 = exposed_ms/集;隐藏部分不计,因为与执行重叠);
3. **CPU 占用**:`solve_ms/决策` 与 `solve_ms/集` 单独报告(用于判断 50/100/500ms 预算档的可行性)。

## 3. 上界与下界的说明

- **下界(乐观)**:只用暴露延迟修正——假设求解与执行完全重叠的场景确实不产生延迟;
- **上界(悲观)**:把全部求解 CPU 时间都算进关键路径(等价于 1ms=1ms)——当前实现同时给出 `solve_ms_per_episode` 供此口径使用;
- 两个口径都报告,真实影响介于其间;正式评估时以**暴露延迟**为主口径(有事件级依据)。

## 4. 已知限制

- 暴露判定用"被选设备在决策时刻空闲"近似"该决策处于关键路径";若同一时刻还有别的任务在排队等待同一设备,暴露可能被高估(保守方向);
- 观测构建(序列化+特征)计入 solve_ms;纯 HiGHS 求解时间可用 `milp_solve_ms` 减去构建时间进一步拆分(后续如需)。
