先纠正两条关键证据

1. Spearman = −1.0，暂时不能写成“目标函数已被证明与真实 JCT 反相关”。

我核对了 misalignment_burst64.json：三个成功样本都只有 2 个可比较动作，其中两个状态来自同一个 episode。

对于只有两个动作、没有并列排名的 Spearman 相关系数，结果必然是 +1 或 −1。所以目前的数据实际证明的是：在这三个可解状态中，旧 MILP 代理目标都把两个动作排反了，平均真实 regret 为 524.2ms。

这值得警惕，但还不足以确定总体相关方向。更重要的是，审计脚本会跳过无法为至少两个动作求出解的状态，存在明显的可解性筛选偏差。Natural 对照甚至是 0 个有效状态，文件中的 mean_spearman=0 只是空样本占位值，不能当作实测零相关。

2. Tail 工作量统计存在可能的加载时间重复计费，需要先修正。

当前 jct_milp_v1_tail_table.py 对未来 GPU 节点使用：

Python
运行
gpu_ms = sum(runtime_p50_ms + load_p50_ms)

但现有模拟器的 predicted_compute_ms() 和 MILP 使用的口径是：

Python
运行
compute_ms = runtime_p50_ms - load_p50_ms

也就是说，runtime_p50_ms 已经按包含加载的总时长处理，再加一次 load_p50_ms 会重复计费。

因此你现在的 stack_a 8.5 秒、stack_b 28.1 秒虽然说明尾部可能很长，但不能直接将这两个数字作为新 MILP 的 GPU 计算时长参数。

应该拆成三个独立量：纯 GPU 计算工作量、CPU/API 延迟、条件性模型加载成本。模型加载是否发生，应由计划中的 GPU 驻留状态决定，而不是在 Tail 工作量里预先无条件计入。

这两项修订完成后，现有数据仍足以支持继续研究新目标，只是不宜把当前证据描述得过于确定。

但规格 §1.1 还有一个关键问题：“全部合法首动作保留”与“只有 K 条链被详细规划”，不自动保证所有动作得到公平比较。

假设有 15 个合法首动作，只为其中 3 个请求预测了完整 H3+Tail，那么这 3 个请求与另外 12 个请求的成本模型就不同。优化器可能只是因为建模精细程度不同而偏爱某些动作。

而且即使只展开 3 条未来链，如果所有 Ready 节点仍参加两两顺序约束，复杂度仍然受整个 Ready 队列规模影响。

这项设计需要在规格中明确：所有候选必须基于可比较的总成本、相同的背景负载与资源约束。可以使用两级架构——先用轻量评分筛选动作，再让 MILP 精细比较 PDRS 与候选——但要如实报告筛选造成的动作覆盖损失，不能称其为全合法动作最优。

建议至少在小规模可穷举状态验证：K 截断是否改变最优首动作，以及改变后产生了多少真实 regret。

裁定 4：允许先不赢 PDRS，但不能作为最终成功门禁

我同意第一轮的目标应该是证明新 MILP 相比旧 MILP 更合理，而不是要求第一版立即击败强基线。

但要区分两种门禁。

阶段性正确性门禁要求：新目标在相同状态和动作集合上，比旧目标具有更好的真实动作排序与更低 regret；所有实际执行的首动作合法；资源约束对齐 DES。

方法价值门禁则进一步要求：新方法相对 PDRS 至少展现出可重复的正向决策增量，并最终在独立 episode 上证明有意义的 JCT 收益，包含或单列在线成本。

尤其不建议继续使用单独的 Spearman > 0 作为硬门槛。三状态、两动作的相关性太不稳定。应该同时看真实 regret、选中最佳动作比例、相对 PDRS 改进与恶化的状态比例，并按 episode 进行不确定性统计。对于只有两个候选动作的状态，直接报告成对排序正确率比 Spearman 更清楚。

还有一点需要强调：旧 MILP 比 PDRS 差，因此新 MILP 显著优于旧 MILP，不代表它已经是值得部署的新方法。

还有三项必须修改的规格问题

P0-A：不能把虚拟 Tail 当成具有真实模型身份的 GPU 节点。

规格 §1.2 让 Tail 直接继承 x/a/c/z/y/q 全部变量，但目前 Tail 表只有总 GPU 工作量，没有未来各模型的执行顺序、驻留需求和峰值工作空间。

因此 Tail 可以在第一版中作为占用 GPU 执行时间的近似资源块，参加指派、排队与同卡互斥；但不能凭空给它指定模型 ID、冷加载状态和驱逐行为，再声称与真实 DES 完全一致。

建议先做不改变模型驻留的计算型 Tail；如果训练数据能够支持，再扩展成少量保留模型身份的尾部阶段。必须分别报告两种表示的预测误差。

P0-B：必须对齐 MILP 计划后续策略与真实反事实的后续策略。

当前错位检验里，MILP 的计划值来自它自己规划的未来节点顺序，而真实反事实值来自强制一个首动作后，继续由 PDRS 调度。

这并不是完全相同的后续策略。

所以现有排序错误可能来自目标截断，也可能来自“规划的后续决策根本没有被执行”。修订后的诊断应同时保留两种检验：

真实 DES 中，强制首动作 + PDRS 后续的 JCT，用于评估实际部署的首动作价值。

在小型闭合世界中，逐步执行 MILP 完整计划的 DES 回放，用于验证它预测的执行计划和目标成本。

两项分开，才能判断主要问题究竟是目标、执行语义，还是滚动重规划带来的策略不一致。

P0-C：Tail 表必须加入统计可靠性门槛。

例如 stack_b|pos10 共有 502 个锚点，但真正继续的只有 2 个，却生成了约 14 秒的尾部均值。

这个估计不能与具有数百个继续样本的桶同等使用。建议预设最低继续样本量（例如 30），不足时回退到更粗粒度的训练先验，并报告估计不确定性。统计检验也应按原始 workflow 来源分组，避免把同一个模板上的多个锚点误当成独立任务。

此外，第一版必须把目前的绝对路径 /Volumes/Lenovo/scheduler 改成仓库相对路径，确保远端和 OpenCode 环境能够复现。
